## Scope change: astrology removed

The business offers four services only (numerology, palmistry, gemstone guidance, color therapy) and has **no astrology service**. At the owner's explicit instruction, all astrology material was removed: the Weekly Horoscope page and its provider interface (`src/lib/horoscope.ts`), the footer link, the How-it-works row, the horoscope feature flag, and the planet names (Sun, Moon, Rahu, Ketu…) that were shown beside the Moolank. `/weekly-horoscope` now redirects to `/free-insight` so old links don't break. A test fails if any page mentions horoscope, zodiac, astrology, Kundli or planets.
**Note:** `PROJECT_BRIEF.md` still lists a weekly horoscope as an approved secondary feature. It has not been edited; it should be updated to match this decision.

## Supabase integration (in progress — Stage 1 of Phase 1 only)

**Done in Stage 1 (nothing connected, nothing visible to customers):**
- Version control initialised; baseline commit tagged `baseline-pre-supabase` (recover the pre-Supabase site with `git checkout baseline-pre-supabase`).
- `@supabase/supabase-js` installed (the only new dependency) and `src/lib/supabase.ts` prepared. It reads only the public URL and publishable key, refuses secret/service-role keys, returns `null` when unconfigured, logs nothing, and is not imported by any page (the production bundle is unchanged).
- `.env.example` documents the two public values; a repository-wide test fails if a secret, service-role identifier, database URL or JWT-shaped token is ever added.

**Stage 3a (sign-up and log-in, built locally — switched OFF, NOT tested against a real Supabase project):** the Sign up, Log in and Dashboard pages now contain real screens in the existing site design. They appear only when `VITE_ACCOUNTS_ENABLED=true` and the two public Supabase values are set; by default these pages still say accounts are not available yet. A single adapter (`src/lib/auth/supabaseAuth.ts`) sits between the site and Supabase, and the sign-in library is loaded only when accounts are switched on, so public pages are no heavier. Tested only with a stand-in backend on this computer (no network): form checks, fixed generic error messages, no account-existence leaks, safe redirects, sign-out, the header link. **Password reset (Stage 3b, same status — built locally, off by default, NOT tested against Supabase):** "Forgot your password?" on the log-in page → `/forgot-password` (always the same neutral answer, never reveals who has an account) → emailed link → `/reset-password` (choose a new password; other logins of that account are signed out, best effort). **Not built yet:** consultation length (not in the database), email notifications, any chat/voice/video system (consultations are arranged manually). **Before switching it on:** the database installed and checked; the Supabase dashboard's URL configuration (Site URL, allowed redirects for `/dashboard` AND `/reset-password`) and the confirmation-email sending set up and tested; the Privacy Policy and Terms reviewed (`supabase/PRODUCTION_READINESS.md` §9).

**Stage 3c (customer journeys, payment reference, admin and expert areas — built locally, OFF by default, tested ONLY against stand-in services, NOT against Supabase):**
- *Customer:* the consultation request flow saves the request through the database when the customer is logged in AND an approved consent version exists (otherwise it keeps the prepare-by-email route and says why). Dashboard: your details (editable), your requests with status/payment/expert, an empty state, a request page with price, payment steps, the UPI reference form (always creates a PENDING claim) and cancel (refused by the database after a verified payment). `/dashboard/security` sets up an authenticator app for anyone logged in (needed before the owner can grant an admin/expert role).
- *Administrator* (`/admin`, loaded on demand): overview counts, request list with filter/search, request page (status steps, expert + time + meeting link, internal notes, verify/reject/refund payments), services and prices, experts, payment settings (UPI ID, payee, instructions), activity log. *Expert* (`/staff`): only requests assigned to them; notes, meeting link, mark completed; no payments.
- *Authenticator step:* administrators and experts must enter an authenticator code in this session (the database enforces it; the screen only helps).
- *Safety design:* every call goes through one adapter (`src/lib/data/supabaseData.ts`) that reads only granted columns, writes payments only through the database functions, and returns fixed error messages only. Static tests check that every column/function the website uses exists and is granted by the migrations (`src/test/schemaAgreement.test.ts`). The screens decide nothing about access: the database does.
- *Honest limits:* a stand-in database that copies the rules is used for screen tests; it is not evidence the real database behaves that way (that was shown only by the simulated isolation test, and real-session tests are still to do). Consultation length, service descriptions and email notifications are not stored/sent. Nothing has been exercised with real emails, real logins, real authenticator codes, or two people at once.

## Decisions & caveats worth knowing

Its claims ("1M+ Seekers", "2000+ People Guided", "Trusted Experts") were **deliberately not reproduced**, since the brief forbids unsupported numbers/credentials.
- **Moolank convention**: day-of-birth reduction (Indian numerology). The traditional themes in `src/data/moolankMeanings.ts` are general and labelled as such; other numerology traditions differ.
- **Email as a stop-gap** puts the request text (including any DOB the user entered) into a `mailto:` link the user themself sends. It is not a secure channel and is a Phase 1 stop-gap only.
- Hosting, domain and deployment: nothing deployed; no accounts or paid services created.
